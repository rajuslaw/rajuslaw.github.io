ENTERPRISE RAG · PROCUREMENT & SUPPLY CHAIN

Contract Intelligence

An enterprise RAG agent that provides procurement and contract-management teams with a single, access-controlled source of truth across fragmented enterprise systems.

Hybrid RAG Cross-Encoder Reranking RBAC Guardrails LLM Failover
Sanitized case study. Internal business-system names are generalized. The architecture and engineering decisions are my own.
01

The problem

Contract information lived in four disconnected systems.

01 Procurement & spend-management

Master contracts and terms.

02 ERP

Purchase orders and payments.

03 Invoicing systems

Invoice information.

04 Regional contract system

Contracts for regions not yet migrated to the main platform.

The resulting problem

The contract team had no single source of truth. They missed rebate opportunities, lacked intelligence during purchase-order placement, struggled to prepare for negotiations, and spent hours manually searching across systems.

Goal

One AI agent — natural-language in, cited answer out — accurate, access-controlled and reliable enough for enterprise procurement decisions.

“What discount does Vendor A offer on electronics?”
“When does our contract with Vendor B expire?”
02

Architecture

The system is deliberately separated into two flows: a batch ingestion pipeline and a real-time query pipeline.

Ingestion is throughput-oriented and reprocessable. The query path is latency-oriented and user-facing.

03

Ingestion pipeline

Data is pulled from the four source systems on a scheduled cadence and lands in an S3 raw landing zone.

flowchart LR A1["Procurement"] A2["ERP"] A3["Invoices"] A4["Regional Contracts"] A1 --> B["Batch ingestion"] A2 --> B A3 --> B A4 --> B B --> C[("S3")] C --> D["ETL"] D --> D1["Metadata"] D --> D2["PII scan"] D --> D3["Classification"] D --> D4["Deduplication"] D1 --> E[("PostgreSQL")] D2 --> F["Embedding"] D3 --> E D4 --> F F --> G[("Pinecone")]
01

Metadata extraction

Vendor ID, contract ID, contract type, region, dates and amounts are extracted and stored in PostgreSQL.

02

PII protection

Documents are scanned for personally identifiable information. Tokenization and masking occur before data moves further into the pipeline.

03

Document classification

Documents are classified as purchase orders, invoices, master contracts or amendments.

04

Deduplication

An MD5 content hash identifies duplicate content and detects document changes.

05

Change propagation

Updates and deletions propagate through the vector store, metadata store and cache to keep the system synchronized.

MD5 is used only for content comparison and deduplication. It is not used as a security primitive.
04

Query pipeline

The query path is optimized for latency, authorization and answer quality.

flowchart TB U["User question"] U --> GW["API Gateway AuthN / AuthZ"] GW --> IG["Input Guardrails PII / Injection / Scope"] IG --> QP["Query preprocessing"] QP --> EMB["Query embedding"] EMB --> HS{"Hybrid search"} HS --> KW["Keyword search"] HS --> SEM["Semantic search"] KW --> RR["Cross-encoder reranker"] SEM --> RR RR --> CTX["Context assembly"] CTX --> LLM["LLM Router"] LLM --> OV["Output validation"] OV --> CI["Citations"] CI --> R["Answer"]
01

Authentication & authorization

The gateway establishes user identity and extracts role/group membership for downstream RBAC filtering.

02

Input guardrails

Microsoft Presidio handles PII, prompt-injection and scope checks early in the request.

03

Query preprocessing

Structured filters such as vendor, region and document type are extracted as predicates.

04

Hybrid retrieval

Keyword and semantic search execute in parallel. Structured metadata provides precision while semantic search captures meaning.

05

Query-time RBAC

Authorization filters are passed directly to the vector query rather than retrieving unauthorized documents and filtering later.

06

Cross-encoder reranking

Search results are merged and reranked using a self-hosted cross-encoder.

07

LLM routing

LiteLLM provides provider abstraction and model failover.

08

Output validation

Responses are checked for PII, sensitive information and grounding before reaching the user.

06

Resiliency

Failure Handling
Vector store unavailable Serve from cache → graceful degradation.
LLM model issue LiteLLM failover to another model.
Provider outage Cross-provider model failover.
Rate limited Cache first; otherwise queue request.
Document corruption Hash mismatch → reconciliation → re-ingestion.
Source deletion Remove embeddings, archive metadata and invalidate cache.
07

Trade-offs

Pinecone Managed vector store

Reduced operational overhead and provided query-time metadata filtering. Trade-off: vendor lock-in and cost at scale.

Self-hosted reranker Cross-encoder

Avoided per-call API cost and kept latency around the desired range. Trade-off: infrastructure ownership.

Hybrid search Keyword + semantic

Combined exact metadata matching with semantic recall. Trade-off: additional system complexity.

Conditional grounding Confidence-based validation

Reduced unnecessary grounding latency for high-confidence responses.

What I'd revisit

03 Introduce parallel search earlier in the design cycle.
04 Add automated fact-checking to complement citation-based human verification.
